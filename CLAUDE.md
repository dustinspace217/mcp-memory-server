# mcp-memory-server — Knowledge Graph MCP Server

Standalone fork of @modelcontextprotocol/server-memory. Provides persistent memory to MCP clients via a knowledge graph of entities, observations, and relations stored in SQLite. (A JSONL flat-file backend existed through v1.5.0 but was retired in v1.6.0; an existing `.jsonl` file is still auto-migrated into SQLite once.)

## Project Goals

This project exists to make a memory server that **actually helps Claude across sessions and compactions** — not to chase theoretical completeness, and not to become a bloated, practically useless mess. The end user is Claude itself: the memory server's job is to be the kind of tool a Claude session would *want* to use — fast, accurate, drift-resistant, and directly useful in the moment.

Every feature must answer the question: *"does this make a real, meaningful improvement to how Claude works across sessions and compactions?"* If the answer isn't a confident yes, the feature doesn't ship. A useless feature isn't neutral — it's friction that crowds out the useful ones and adds maintenance, test surface, and cognitive load with no payback.

### The three durable goals (A/B/C)

These are the evaluation criteria for every design decision in this project. Originally established for the memory freshness hook system (`~/.claude/projects/-home-dustin-Claude/memory/project_memory_system_goals.md`), they apply identically here because the freshness system and the memory server serve the same end: trustworthy, useful recall.

- **A. Reduce drift and hallucination risk.** Stale facts must surface, not be silently recalled as truth. Every code path that exposes data is responsible for distinguishing "currently true" from "was true at time T."
- **B. Faithful recall of who/what/when/where/why/how** for projects, conversations, actions, decisions. The memory server is the canonical record of how a body of work came to be the way it is. Losing that history defeats the purpose.
- **C. Enhance meaningful conversations and quality code.** These are the two end-uses memory serves. A feature that doesn't trace back to one of them — directly or one hop away — doesn't belong in this project.

### Goal-first evaluation

When a design decision arises (coverage gap, scope ambiguity, trade-off), map the options against the three goals and the practical principle above, and pick the option that serves them best. **Implementation conventions are means, not ends.** If a convention conflicts with a goal, the goal wins. Don't escalate to the user until goal-first analysis fails to produce a clear answer. (Durable workflow rule from `feedback_goal_first_evaluation.md`.)

### Anti-bloat gate (mandatory before adding any new tool, schema column, or code path)

1. **Goal trace.** Does this serve A, B, or C in a way the existing tools don't already cover? Name the gap.
2. **Practical use test.** Would a Claude session actually reach for this in the moment, or is it shelf decoration nobody invokes?
3. **Cost proportionality.** Is the cost (complexity, maintenance, test surface, RAM at runtime) proportional to the practical benefit?

If any answer is no, drop it or defer it to a later version. **Three usable tools beat ten clever ones nobody reaches for.** When in doubt, leave it out — features can always be added later if the gap proves real, but removing a shipped feature is much harder.

### Why these goals are written here

This section exists so any future Claude session opening this project sees the *animating purpose* before the *technical detail*. The risk this guards against is straightforward: a memory server that grows feature-by-feature without a north star eventually becomes the thing it was supposed to replace — slow, noisy, and untrustworthy. The goals above are the north star.

## Tech Stack
- TypeScript, Node.js 22, ES modules
- MCP SDK: @modelcontextprotocol/sdk (stdio transport)
- better-sqlite3 for SQLite storage (native C addon — requires C build tools at install time)
- sqlite-vec for vector similarity search (native SQLite extension via npm)
- @huggingface/transformers for local ONNX embedding generation (384 dimensions; default all-MiniLM-L6-v2, env-switchable — this deployment runs granite-embedding-small-english-r2 via the onnx-community mirror since the 2026-07-02 G3 cutover)
- Zod for input/output schema validation
- Vitest for testing
- Build: `npm run build` (tsc)
- Test: `npm test` (vitest run)

## Architecture

The server is split across these source files:

### `types.ts` (~535 lines)
- Defines the `Entity`, `Relation`, `KnowledgeGraph`, and `Observation` types
- Context-graph types (v1.2.0): `ConnectedNode` / `ConnectedContextOptions` / `ConnectedContextResult` (the latter carries `cycles: string[][]`) for `getConnectedContext`; `PrecedentMatch` / `FindPrecedentsOptions` / `FindPrecedentsResult` for `findPrecedents`. Both methods are declared on the `GraphStore` interface.
- `RelationInput` type: 3-field input (from, to, relationType) for creating/deleting relations — callers never construct temporal fields
- `Relation` type: 5-field output (from, to, relationType, createdAt, supersededAt) — temporal fields are system-managed
- `InvalidateRelationInput` type: identifies relations to retire via `invalidateRelations()`
- `Entity.project: string | null` — scopes the entity to a project (`null` = global, never `undefined`)
- `Entity.updatedAt: string` and `Entity.createdAt: string` — ISO 8601 UTC timestamps (sentinel `'0000-00-00T00:00:00.000Z'` for legacy data)
- `CreateEntitiesResult` and `SkippedEntity` types — collision reporting when entity names already exist
- `PaginationParams`, `PaginatedKnowledgeGraph`, `InvalidCursorError` types for cursor-based pagination
- `SupersedeInput` type: `{ entityName, oldContent, newContent }` for observation supersede operations
- `SetObservationMetadataInput` type: `{ entityName, content, importance?, contextLayer?, memoryType? }` — updates metadata on active observations without superseding. Uses `'key in object'` checks to distinguish "omitted" from "explicitly null".
- `ContextLayerObservation` and `ContextLayersResult` types — return types for `getContextLayers()`. L0 observations omit `updatedAt`, L1 includes it. `tokenEstimate` is chars / 4.
- `TimelineObservation`, `TimelineRelation`, `EntityTimelineResult` types for full entity history (active + superseded items with computed `status` field)
- `SimilarObservation` type: `{ content, similarity }` returned when newly added observations are semantically close to existing ones (cosine > 0.85)
- `AddObservationResult` includes optional `similarExisting?: SimilarObservation[]` for similarity warnings
- Defines the `GraphStore` interface — the contract both storage backends must implement
- All CRUD methods are declared here; `SqliteStore` implements this interface (the sole live backend since the v1.6.0 JSONL retirement)
- `createRelations(relations: RelationInput[])` and `deleteRelations(relations: RelationInput[])` use the input type; return `Relation[]` (with temporal fields)
- `invalidateRelations(relations: InvalidateRelationInput[])` — marks relations as superseded (idempotent)
- `entityTimeline(entityName, projectId?)` — returns full history including superseded observations and invalidated relations
- `supersedeObservations(supersessions: SupersedeInput[])` method on `GraphStore` — atomically retires old observations and inserts replacements
- `getContextLayers(projectId?, layers?)` method on `GraphStore` — returns L0/L1 observations with token budget enforcement; two-tier since v16 (`L1IndexEntry` + optional `ContextLayersResult.L1Index`)
- `getSummary(projectId?, excludeContextLayers?, limit?)` method on `GraphStore` — returns session-start briefing snapshot: top observations by importance, recently updated entities, aggregate stats
- `setObservationMetadata(updates: SetObservationMetadataInput[])` method on `GraphStore` — updates importance/contextLayer/memoryType in-place on active observations; returns count updated
- Updated `GraphStore.readGraph` and `GraphStore.searchNodes` signatures accept `PaginationParams` and return `PaginatedKnowledgeGraph`
- `Observation` type: `{ content: string; createdAt: string }` — each observation carries an ISO 8601 UTC timestamp (or `'unknown'` for data migrated from old string format)

### `rank-fusion.ts` (~110 lines)
- Pure ranking math for hybrid search (v1.3.0 Phase A/B) — no DB, no model, unit-testable in Pool 1 (same rationale as `rankAndFloorPrecedents`)
- `fuseRanks<K>(lists)` — weighted Reciprocal Rank Fusion (`score = Σ weight/(60+rank+1)`). Rank-based (not score-based) so BM25/cosine/recency/activation never need cross-scale normalization. `RRF_K = 60` (literature standard, deliberately not configurable)
- `toFtsQuery(raw)` — FTS5 MATCH sanitizer: strips NUL bytes, DROPS tokens containing no letter/digit (they tokenize to empty phrases — probed 2026-07-02: tolerated in AND chains on current SQLite but undocumented, and a lone one matches nothing), then wraps every surviving token in double quotes (embedded `"` doubled) so operators in user input (AND/OR/NOT/NEAR/*/^/-) match literally. User input must NEVER reach MATCH unsanitized. Round-trip-tested against the real FTS5 parser with a hostile corpus
- `activationScore(count, lastAccessedAt, nowMs)` — ACT-R base-level activation approximation `ln(1+n) − 0.5·ln(1+hours)`; -Infinity for never-accessed/sentinel; clamps future timestamps (multi-instance clock skew). Consumed by Phase B's activation rerank list

### `pagerank.ts` (~100 lines)
- `personalizedPageRank(edges, seeds, opts?)` — bounded personalized PageRank over the active relation graph (v1.3.0 Phase E, HippoRAG-2-inspired). Pure function, Pool 1-testable: undirected degree-normalized push, alpha=0.5 restart to normalized seeds, 3 iterations (~3-hop reach, matching get_connected_context's default horizon). Self-loops dropped; nodes never reached are absent from the result (callers treat absent as zero). Consumed by `findPrecedents`' `rerank` path (seeds = candidate observations' parent entities at best cosine)

### `context-layers.ts` (~110 lines)
- Two-tier L1 logic for `getContextLayers()` (v16, spec §13) — pure functions + constants, Pool 1-testable. Originally the single source of truth across BOTH backends (building it surfaced a real drift: the JSONL backend's local L1 budget had slipped to 3200 chars while SQLite's was 16000); SQLite-only since the v1.6.0 retirement, but kept factored out as pure, independently-testable logic
- `L1_FEATURED_CHAR_BUDGET = 12000` / `L1_INDEX_CHAR_BUDGET = 4000` — the v16 split of the historical 16000-char single budget: featured = full text most-important-first (identical to pre-v16 behavior at the smaller budget); index = per-entity breadcrumbs for everything else, replacing silent truncation with a visible map
- `buildL1Index(unfeatured)` — groups unfeatured L1 observations by entity (first-seen order = max-importance order since input is importance-DESC), builds hints (`summary ?? first 100 chars`, comma-joined, ≤200 chars), budgets on SERIALIZED entry length, drops lowest-importance entities first, always keeps the first entry
- `indexCharCost(entries)` — serialized char cost for the caller's tokenEstimate

### `cursor.ts` (~120 lines)
- Shared cursor utilities for keyset pagination — used by both store backends
- `CursorPayload` interface: `{ u, i, n?, q }` — sort position + query fingerprint
- `encodeCursor()` / `decodeCursor()`: base64 JSON encoding with structural validation
- `decodeCursor` validates: `i` is non-negative finite integer, `n` is string if present, `q` matches expected fingerprint
- `clampLimit()`: clamps page size to [1, MAX_PAGE_SIZE] with DEFAULT_PAGE_SIZE fallback; floors fractional input (direct GraphStore callers bypass Zod's `.int()` — a fractional limit would flow into computed KNN parameters)
- `readGraphFingerprint()` / `searchNodesFingerprint()`: build query fingerprints using null byte (`\0`) separator to prevent collision when projectId/query contains delimiter characters
- Constants: `DEFAULT_PAGE_SIZE = 40`, `MAX_PAGE_SIZE = 100`

### `normalize-name.ts` (~80 lines)
- `normalizeEntityName(input: string): string` — Layer 1 entity-name normalizer used as the identity key throughout the store
- Deterministic, no semantic understanding: trim → Unicode NFC → strip Unicode Format chars (`/\p{Cf}/gu` — zero-width space/ZWNJ/ZWJ/BOM/soft-hyphen/word-joiner, so invisible copy-paste artifacts can't create duplicate identity keys, Issue #59) → lowercase → strip separators (`/[\s\u0000-\u001f\-_/.\\:]+/g`) → reject empty. The Cf strip is a SEPARATE `/u`-flagged replace: `\p{Cf}` requires `/u`, but the separator class has no `/u` and must not gain one (it changes escape semantics).
- The separator class includes the **whole C0 control range** (`\u0000-\u001f`), not just `\s` (which only covers `\t\n\v\f\r`). This guarantees a normalized name can never contain `char(31)` (0x1f), which `get_connected_context` uses as its recursive-CTE path/cycle-guard delimiter — a name carrying 0x1f would split a path mid-name and corrupt cycle detection.
- Why NFC (not NFKC): NFC preserves visual identity. NFKC would collapse typographic forms like `ﬁ → fi` and `Ⅸ → IX`, destroying information when the user genuinely meant the ligature or roman numeral.
- Callers: `SqliteStore` mutation/lookup paths (entities + relation endpoints) and `index.ts` tool boundary handlers — surface variants like `Dustin-Space`, `dustin/space`, `DUSTIN SPACE`, and `dustinspace` all map to the same identity key `dustinspace`.
- Display form is preserved in the `entities.name` column (see `sqlite-store.ts`); this module only produces the identity key.
- Turkish dotted-I caveat: `toLowerCase()` uses default locale — `İ` → `i̇` (i + combining dot). Acceptable for English-dominant projects; documented limitation.
- Throws `Error` on empty input or input that normalizes to empty (e.g. whitespace-only or separator-only name).

### `relation-types.ts` (~60 lines)
- Documented core causal/precedent relation vocabulary so "why does this rule exist / what incident caused it" is a relation lookup, not a prose grep.
- `CORE_RELATION_TYPES` — frozen array of the three first-class verbs: `CAUSED_BY` (effect → cause), `PRECEDENT_FOR` (earlier → later), `SUPERSEDES` (newer → older). `CoreRelationType` is the union type.
- `RELATION_TYPE_GUIDANCE` — a human-readable directionality block (the same content as the design spec's Appendix B) that `index.ts` appends to the `create_relations` tool description, so the agent sees the canonical verbs + their from→to direction at call time.
- **Write-time canonicalization (v1.3.0 Phase C2, both backends):** `relationTypeKey()` (trim → lowercase → whitespace/hyphens → `_`) keys incoming types; core vocabulary wins its canonical casing, exactly ONE existing active spelling with a matching key is reused, novel types store verbatim (DEF-CG-03's open vocabulary stands), and ambiguous keys (multiple pre-v13 spellings — the "ambiguity ratchet") are never guessed between: verbatim until data repair retires one spelling. `RELATION_VOCAB_FIXES` — the frozen v13 migration map (consumed only by the migration; C2 uses live lookups).

### `embedding.ts` (~215 lines)
- `EmbeddingPipeline` class: wraps `@huggingface/transformers` for local ONNX embedding generation
- `VectorState` type: `{ status: 'loading' } | { status: 'ready'; pipeline } | { status: 'failed'; error; failedAt } | { status: 'unavailable' }` — logged at every transition
- `startLoading(onReady?)`: background model load via dynamic `import('@huggingface/transformers')`. Calls `onReady` callback when model is ready.
- `embed(text, kind?)`: single text → Float32Array(384) embedding with circuit breaker (5 consecutive failures → 'failed'). `kind` (v1.3.0 G1): `'passage'` (default — stored observations, dedup comparisons) or `'query'` (search/precedent lookups — the ONLY side that receives the configured instruction prefix; identical under the MiniLM default)
- `embedBatch(items)`: sequential per-item embedding with error isolation (failed items skipped, rest continue)
- **Env-configurable (G1)**: `MEMORY_EMBED_MODEL` (default `Xenova/all-MiniLM-L6-v2` = `DEFAULT_EMBED_MODEL`), `MEMORY_EMBED_POOLING` (`mean` default | `cls` — a mean/cls mismatch is a SILENT ~4% cosine drift, so it must switch WITH the model), `MEMORY_EMBED_QUERY_PREFIX` (default '' — retrieval-specialized models like arctic/bge are asymmetric and need it on queries only). A model switch = env flip + restart: the v15 vec_config guard clears stale vectors and the sweep re-embeds.
- **Cosine gates, env-configurable (G3, 2026-07-02)**: `MEMORY_SIMILAR_THRESHOLD` (default 0.85), `MEMORY_DUPLICATE_THRESHOLD` (0.80), `MEMORY_PRECEDENT_FLOOR` (0.25), and `MEMORY_TRIGGER_THRESHOLD` (default 0.50, v1.7.0 — the `check_prospective_triggers` firing gate, sitting between the precedent floor and the similar warning because firing INTERRUPTS with a payload) — resolved here beside the model envs because they are model-geometry-coupled and must move WITH the model (granite's random-pair cosine median ~0.77 vs MiniLM's ~0.11). Garbage values warn loudly + fall back. Recalibrate per model with `scripts/recalibrate-thresholds.py` (percentile-held mapping); the live granite deployment runs 0.969/0.934/0.798 from the 2026-07-02 run (a recalibrated trigger value is set at deploy, not baked). Tool descriptions interpolate the resolved values.
- `prefixedInput(text, kind, prefix?)` pure helper; `EMBEDDING_DIM = 384` (the vec0 schema is fixed — candidates must be 384-dim or MRL-truncatable)

### `jsonl-reader.ts` (~190 lines) — migration parser only (v1.6.0)
- The read half of the retired `JsonlStore`, kept ONLY as the SQLite upgrade path. NOT a `GraphStore` — no writes, no queries, no lifecycle; it exists so a deployment still holding a `.jsonl` file has a data-preserving path into SQLite (workspace rule: data-preserving before data-destructive).
- `readJsonlGraph(path)` — slurps a `.jsonl` file into a `KnowledgeGraph` for one-time migration: per-line error isolation (malformed lines logged to stderr and skipped) plus the backward-compat deserialization the old loader carried (missing `project` → null, missing relation temporal fields → defaults, optional valid-time, legacy string observations widened, `summary` carry-through). Consumed by `SqliteStore.init()`'s migration and crash-recovery paths.
- `normalizeObservation(obs)` — legacy string-or-object observation → `Observation`. Re-exported from `index.ts` for external consumers that used to import it from `jsonl-store`.
- `migrateJsonToJsonl(scriptDir, jsonlPath)` — the legacy `memory.json` → `memory.jsonl` rename, the FIRST hop of the upgrade chain (`json` → `jsonl` → `db`); only fires for the default `memory.jsonl` path.

### `evict.ts` (~300 lines)
- Four-tier degradation and size-pressure eviction module implementing §12 of the v1.1 design spec
- `checkAndEvict(db, dbPath)`: main entry point — checks if DB size exceeds 90% of cap, runs eviction sweep if so
- Tier 1: hard-delete tombstoned entities (tombstoned_at > 1 year, last_accessed_at > 6 months)
- Tier 2: tombstone superseded entities (superseded_at > 1 year, last_accessed_at > 6 months) — strips observation content, preserves skeleton
- Never hard-deletes active data on size pressure alone
- LRU shield: entities accessed within 6 months are protected at every tier
- **CRITICAL: uses raw SQL through better-sqlite3 Database handle directly** — NOT through any GraphStore method. The eviction sweep is a consumer of `last_accessed_at`, never a producer. Routing through GraphStore would update `last_accessed_at` on every scanned entity, defeating the LRU shield (the "observer effect" from §12).
- `getCapBytes()`: reads `MEMORY_SIZE_CAP_BYTES` env var, defaults to 1 GB
- Batch processing (BATCH_SIZE=500) to avoid blocking the main loop
- `EvictionResult` interface: `{ triggered, hardDeleted, tombstoned, dbSize }`

### `sqlite-store.ts` (~3900 lines)
- `SqliteStore` class: SQLite backend using `better-sqlite3`
- Implements the `GraphStore` interface
- **Prospective memory (v1.7.0):** `prospective_triggers` table (id/trigger_text/payload/project/created_at/fired_at; fired_at '' = pending, ISO = fired, one-shot) + `vec_triggers` vec0 table (created ALONGSIDE vec_observations in the vector-setup block, not the versioned migration — same optional-extension gate; only PENDING triggers hold a vec row). `setProspectiveTrigger` inserts + fire-and-forget embeds the condition (`syncTriggerEmbedding`, passage kind, never throws; `runTriggerEmbeddingSweep` catches un-embedded pending triggers after model load). `checkProspectiveTriggers` embeds context once (query kind), KNN over `vec_triggers`, fires every pending in-scope trigger ≥ threshold (raw cosine, display-rounded) in ONE transaction (stamp fired_at + drop vec row), degrades to `{ fired: [], vectorSearchEnabled: false }` when the model/vec table is unavailable (no fallback). `listProspectiveTriggers` (pending-only by default), `deleteProspectiveTriggers` (HARD delete + vec-row removal — deliberate exception to the preservation lifecycle: triggers are ephemeral intent). The v15 model-switch guard's DELETE clears `vec_triggers` too; startup orphan cleanup drops vec rows for non-pending triggers.
- **Provenance (v1.7.0):** `observations.source_ref TEXT NOT NULL DEFAULT ''` — optional caller-supplied `sourceRef` threaded through `createEntities`/`addObservations`/`supersedeObservations` (replacement rows), surfaced in all observation hydrations + `entityTimeline` (absent when '' — same convention as valid-time).
- **Context-graph methods (v1.2.0):** `getConnectedContext(seedEntity, opts)` — bounded multi-hop traversal via a `WITH RECURSIVE` CTE (direction-aware `edges` CTE materialized once per call; per-path char(31)-delimited cycle guard; `GROUP BY node` + `MIN(depth)` collapses multi-path arrivals to the nearest hop). The seed is resolved project-independently (it's the anchor, not a scoped node); reached nodes are hydrated + project/temporal-filtered BEFORE the `maxNodes` cap so `truncated` stays honest. `detectDirectedCycles(relations)` — gray/black-coloring DFS over the returned edges; dedups by node-SET via `JSON.stringify(sorted)` (collision-proof + legible). `findPrecedents(query, projectId, opts)` — KNN over `vec_observations` (mirrors the dedup path), hydrate active/in-scope, then `rankAndFloorPrecedents` (module-level pure helper) gates on the raw-cosine floor, ranks raw-DESC, caps, and rounds for display only. Degrades to empty+flags (no recency fallback) when the model/vec table is unavailable.
- **Schema version tracking**: `schema_version` table with `CHECK(id=1)` single-row constraint. Versions 1–15 tracked. Legacy databases detected via column existence heuristics and assigned an initial version. All migrations run in sequence on startup.
- **Entity name normalization (v8)**: `entities.normalized_name` is the identity key (lowercased + NFC + separators stripped, produced by `normalize-name.ts`). `entities.name` preserves the original display form the user typed. All lookups and uniqueness constraints use `normalized_name`; tool output surfaces `name`. Partial unique index `idx_entities_normalized_active ON entities(normalized_name) WHERE superseded_at = ''` enforces one active identity per normalized key.
- **Relations store normalized endpoints (v8)**: `relations.from_entity` and `relations.to_entity` hold the normalized identity keys — not display names — so lookups work regardless of which surface variant the caller used. `readGraph()` and `searchNodes()` translate endpoints back to display form via `LEFT JOIN entities ON ... COALESCE(e.name, r.from_entity)` so output always shows the user's original capitalization/separators. v6→v7 migration drops the FK clause from `relations.from_entity`/`to_entity` (the underlying `entities.name` UNIQUE constraint is now partial, and partial unique indexes don't qualify as FK targets in SQLite); integrity is enforced by the v8 migration's explicit orphan check and the tool-boundary normalization.
- `project TEXT` nullable column on entities table — `NULL` means global (visible to all projects)
- `updated_at` and `created_at` columns on entities table (sentinel default for legacy data, backfilled from observation timestamps during migration in a transaction)
- `superseded_at TEXT NOT NULL DEFAULT ''` on observations — empty string sentinel means active, ISO timestamp means superseded. `UNIQUE(entity_id, content, superseded_at)` constraint. All queries filter `WHERE superseded_at = ''` to exclude retired observations.
- `idx_observations_active` partial index on `observations(entity_id) WHERE superseded_at = ''`
- **Temporal relations**: `created_at TEXT NOT NULL DEFAULT ''` and `superseded_at TEXT NOT NULL DEFAULT ''` on relations table. `UNIQUE(from_entity, to_entity, relation_type, superseded_at)` constraint. Active queries filter `WHERE superseded_at = ''`. Schema v4→v5 migration uses table rebuild pattern.
- `invalidateRelations()`: sets `superseded_at` to current timestamp on matching active relations. Idempotent — ignores already-invalidated relations.
- `entityTimeline()`: returns full history of an entity — ALL observations and relations (active + superseded) sorted chronologically with computed `status` field.
- `supersedeObservations()` atomically retires old observations and inserts replacements in a single transaction
- Migration via `pragma('table_info')` for existing databases — table rebuild migration for superseded_at column
- Phase 4 migration (timestamps) wrapped in explicit transaction — prevents crash between ALTER TABLE and backfill from leaving permanent sentinel timestamps
- **Vector search**: loads `sqlite-vec` extension, creates `vec_observations` virtual table (`vec0` with 384-dim float vectors + `+observation_id TEXT NOT NULL` auxiliary column). Startup orphan cleanup removes vec rows without matching active observations. Background embedding sweep generates embeddings for un-embedded observations after model loads. Sweep has `.catch()` on the promise (prevents unhandled rejection crash), try-catch around batch INSERTs, and DELETE-before-INSERT to prevent duplicate vec rows from races with `syncEmbedding()`.
- `syncEmbedding()` centralized helper — all 5 mutation paths (create, add, delete, deleteEntity, supersede) fire-and-forget it to keep `vec_observations` in sync. Never throws (internal try-catch), never awaited on mutation paths so MCP responses return immediately after the sync transaction.
- **Similarity check** in `addObservations()`: after inserting new observations, embeds them and runs KNN search against same-entity observations. Returns `similarExisting` array (cosine > 0.85) in the response for deduplication awareness.
- Hybrid `searchNodes()`: runs LIKE query first, then augments with KNN vector results if embedding model is ready. Vector-only matches are appended to LIKE results, deduped against full LIKE match set across all pages.
- **Relevance mode (v1.3.0 Phase A+B):** `searchNodes(..., orderBy: 'relevance')` branches after the shared `matched_ids` CTE into `searchNodesRanked()` — weighted RRF (via `rank-fusion.ts`) over four entity-level candidate lists: LIKE (recency-ordered, weight 1.0), FTS/BM25 best-per-entity (1.0), vector KNN best-cosine-first (1.0, skipped unless model ready), and ACT-R activation (0.5 — computed ONLY over the union of the other three lists: activation reranks candidates, never nominates; never-accessed entities are excluded rather than tail-ranked so no-history contributes exactly nothing). Top-k only: `nextCursor` always null; store-level guard THROWS on cursor or asOf combined with relevance (rank is query-relative/mutation-unstable; FTS holds current content only) — this guard is the ONLY enforcement point (registerTool's per-field ZodRawShape cannot cross-field-validate). `rankingDegraded?: ('fts'|'vector')[]` surfaces lost candidate lists to the caller (goal A — degradation changes result MEMBERSHIP): set on FTS/vector query failure or model still loading/failed; deliberately NOT set when vector search is configured off. `totalCount` in relevance mode = fused-candidate-union size at collection time (may exceed returned entities under concurrent mutation — documented semantic, not a bug). Default `'recency'` is byte-identical to pre-v1.3.0 behavior.
- `idx_relations_to_entity_active` partial index on `relations(to_entity) WHERE superseded_at = ''`; `idx_entities_project_updated(project, updated_at DESC, id DESC)` and `idx_entities_updated(updated_at DESC, id DESC)` indexes for paginated reads
- Single-column `idx_entities_project` dropped on startup (redundant — covered by composite `idx_entities_project_updated`)
- **Graceful shutdown**: `private shuttingDown` flag checked in `runEmbeddingSweep` loop. `shutdown()` method sets the flag. Called from SIGINT/SIGTERM handlers before `close()`.
- **Eviction integration**: `maybeRunEviction()` private helper increments a write counter and calls `checkAndEvict()` (from `evict.ts`) every 1000 writes. Also runs a startup eviction check in `init()`. All 9 write methods call `maybeRunEviction()` at the end.
- **`last_accessed_at` access discipline**: `touchEntities()` and `touchEntitiesByName()` private helpers update the timestamp. Called by: `searchNodes`, `openNodes`, `entityTimeline`, and all write operations. NOT called by `readGraph` (bulk reads aren't intentional access). The eviction sweep never touches `last_accessed_at` (uses raw SQL in evict.ts). Since v12, `access_count` increments under the PARITY RULE at exactly these sites (see the v11→v12 migration entry).
- **`tombstoned_at`** columns on entities, observations, and relations (v9). Tombstoned entities have `superseded_at != ''` (from original soft-delete) so existing `WHERE superseded_at = ''` filters already exclude them from active queries. The `tombstoned_at` column is only meaningful for the eviction sweep and `entityTimeline()` output (which shows `'tombstoned'` status for stripped observations/relations).
- Opens the database with WAL mode (Write-Ahead Logging) — allows reads to proceed concurrently with writes
- `foreign_keys = ON` is set per connection — SQLite does not enable FK constraints by default, so this must be set explicitly each time the connection opens
- Deduplication is enforced at the database level via `UNIQUE` constraints on entity names, relation triples (+ superseded_at), and (entity + observation content + superseded_at) — `INSERT OR IGNORE` silently skips duplicate inserts
- Relations must reference existing entity names (FK constraints), so adding a relation with a missing endpoint throws rather than silently creating a dangling edge
- Cursor-based keyset pagination on `(updated_at DESC, id DESC)` — imports cursor utilities from `cursor.ts`
- `openNodes` uses IN-clause chunking (CHUNK_SIZE=900) for consistency with other methods

## Memory Maintenance

### Observation write guidance
- **Supersede** when an observation states a fact that has changed (status, counts, signatures, descriptions). Use `supersede_observations` to atomically retire the old observation and insert the updated version. The old observation remains in the database (with a `superseded_at` timestamp) for history but is filtered from all active queries.
- **Append** when an observation adds a genuinely new fact that doesn't contradict or update any existing observation. Use `add_observations` as before.
- **Delete is now a soft-retire, not destruction.** `delete_observations` stamps `superseded_at` (recoverable via `as_of` / `entity_timeline`), exactly like supersede — it no longer hard-`DELETE`s the row. Use **supersede** when replacing an observation with updated content; use **delete** to retire one that has *no* replacement (e.g. pure noise). Permanent removal happens only through the eviction sweep, never a direct call. (Historically `delete_observations` was a hard `DELETE FROM`; corrected to soft-delete so it stops being the one path that bypassed the preservation-biased lifecycle.)

### Vector search
- Vector search uses sqlite-vec + @huggingface/transformers (384-dim; MiniLM default, granite-r2 on this deployment via env — see the G3 cutover in the 2026-07-02 plan doc). The three cosine gates (similarExisting/check_duplicates/precedent floor) are model-geometry-coupled env knobs resolved in embedding.ts; a model switch without moving them silently breaks dedup (granite's random-pair cosine median is ~0.77 vs MiniLM's ~0.11 — recalibrate with scripts/recalibrate-thresholds.py)
- LIKE substring search always runs; vector search adds supplementary semantic matches when the model is loaded
- Set `MEMORY_VECTOR_SEARCH=off` env var to disable vector search entirely
- On first startup, the model downloads ~23MB (cached thereafter). Embedding sweep runs in background.
- `syncEmbedding()` in sqlite-store.ts is the centralized helper — all mutation paths call it

## Known Limitations
- **Entity names are globally unique** across all projects — permanent architectural constraint because relations use entity names as foreign keys
- **Project filtering is advisory, not a security boundary** — it scopes queries for convenience but does not enforce access control. Entity name collisions across projects are reported (not silently dropped), and global entities (project=null) are visible to all project-scoped queries by design.
- **JSONL backend retired (v1.6.0)**: SQLite is the only live backend. An existing `.jsonl` file is auto-migrated into SQLite once (via `jsonl-reader.readJsonlGraph`); a `.jsonl` `MEMORY_FILE_PATH` with no file behind it throws the retirement error. `jsonl-store.ts` and its `GraphStore` implementation are deleted.
- **SQLite backend**: LIKE-based search is case-insensitive for ASCII only — non-ASCII Unicode characters (e.g. accented letters, CJK) may not match case-insensitively as expected. The FTS candidate list in relevance mode partially mitigates this (unicode61 tokenizer folds case + diacritics), but the LIKE list keeps the ASCII limitation
- **Relevance mode is top-k only** — `orderBy:'relevance'` returns the top `limit` fused results with `nextCursor: null`; combining it with `cursor` or `asOf` throws (rank is query-relative and mutation-unstable; the FTS index reflects current content only).
- **Paginated relations use either-endpoint semantics (v1.4.0)** — a page carries every relation touching one of its entities; the partner endpoint may not be on the same page (it's a name — `open_nodes` it for content). A spanning relation appears on each endpoint's page, so dedup on (from, to, relationType) when unioning; the deduped union across all pages IS the complete active relation set (verified on a live-DB copy: 496/496; the pre-fix page-local AND filter returned 156 of 474 — the 2026-06-23 audit). Project-scoped reads still exclude cross-project relations, filtered against the whole project + global entity set rather than the page.
- **Cursor stability under mutation** — if an entity's `updatedAt` changes between page fetches (e.g., observations added), the entity may appear on two pages or be skipped. This is inherent to keyset pagination with a mutable sort key and is the correct tradeoff for a memory server (freshness > perfect enumeration). Note: SQLite gracefully continues past deleted cursor targets (keyset WHERE clause skips missing rows).
- **Vector search is best-effort** — if the model fails to load, the extension is unavailable, or embedding fails for specific observations, the system degrades gracefully to LIKE-only. No data is lost.
- **Embedding latency on writes** — embedding generation is fire-and-forget after the sync transaction commits (does not block MCP response). Embedding may not be searchable until the next query (~5-15ms per observation).
- **vec0 is brute-force KNN** — at current scale (~1500 observations), sub-millisecond. At ~50,000+, consider switching to ANN index (sqlite-vec supports IVF).
- **Pagination sorts by `updatedAt`, not semantic relevance** — vector search improves recall (finding entities LIKE would miss) but does not affect ranking.
- **Valid time is caller-supplied and record-only (v14)** — the server stores `validFrom`/`validUntil` but does not extract dates from content and offers NO valid-time query filtering yet (an `as_of_valid` param waits for a demonstrated need — DEF-RR-01 in the 2026-07-02 plan).
- **Context layers are caller-managed** — the server stores `context_layer` values (L0/L1/null) but does not auto-assign or auto-promote observations. The caller (Claude hooks, tools) is responsible for classifying observations into tiers.
- **Prospective triggers are tool-driven and vector-only (v1.7.0)** — firing happens only when a caller invokes `check_prospective_triggers` with context (no automatic SessionStart-hook firing yet — DEF-PM-01). Matching is purely semantic (KNN over `vec_triggers`); with vector search off/unavailable, check returns `{fired:[], vectorSearchEnabled:false}` and NEVER substring-falls-back. Firing is one-shot (a fired trigger is retired from matching).
- **Provenance (source_ref) is caller-supplied and record-only (v1.7.0)** — the server stores `sourceRef` verbatim and surfaces it in reads/entity_timeline, but does not extract it from content and offers NO query filtering by it. Adoption follows the same curve as valid-time: '' for most writes until capture prompts/hooks pass a session id (harness follow-up, not builder scope).
- **`memory_type` is free-form** — any string is accepted; there is no server-side validation of allowed values. Convention enforcement is the caller's responsibility. Known types: `decision`, `procedure`, `architecture`, `problem`, `preference`, `status`, `fact`, `emotional`. A typo in `memoryType` filter returns empty with a hint only when the string isn't in the known-types list.
- **`memoryType` + vector search for sparse types** — KNN retrieves top-k globally, then filters by `memory_type`. If a type has very few observations relative to the corpus, they may not appear in the global top-k and the vector search returns empty for that type. LIKE substring search is unaffected. Mitigated by using a larger k (200) when `memoryType` is set, but not eliminated for extremely sparse types at large scale.
- **Eviction is best-effort** — the eviction sweep runs at startup and every ~1000 writes. If the DB grows past the cap between checks (e.g., a single massive batch insert), it will be caught on the next check. The 1 GB default cap can be overridden via `MEMORY_SIZE_CAP_BYTES` env var.

## Schema Migrations
Database schema is versioned in the single-row `schema_version` table (CHECK constraint enforces one row). Migrations run in sequence on startup in `sqlite-store.ts`; each one is idempotent and wrapped in a transaction except where noted.

- **v1→v2:** Baseline schema for initial entity/observation/relation tables.
- **v2→v3:** `project TEXT` nullable column on entities (NULL = global).
- **v3→v4:** `updated_at` / `created_at` columns on entities with observation-timestamp backfill in a single transaction.
- **v4→v5:** Temporal relations — `created_at` + `superseded_at` on relations with `UNIQUE(from_entity, to_entity, relation_type, superseded_at)`. Table-rebuild migration.
- **v5→v6:** Observation metadata — `importance REAL DEFAULT 3.0`, `context_layer TEXT NULL`, `memory_type TEXT NULL` on observations.
- **v6→v7:** Soft-delete on entities — `superseded_at TEXT NOT NULL DEFAULT ''` column, partial unique index `idx_entities_name_active ON entities(name) WHERE superseded_at = ''`. FK clauses on `relations.from_entity`/`to_entity` are dropped in this migration because partial unique indexes don't qualify as FK targets in SQLite.
- **v7→v8:** Entity name normalization — adds `normalized_name` column on entities (the identity key), rewrites `relations.from_entity`/`to_entity` to normalized form, drops `idx_entities_name_active`, creates `idx_entities_normalized_active ON entities(normalized_name) WHERE superseded_at = ''`. Collision check before index creation aborts the migration (rollback) if two active rows normalize to the same key, naming both display forms and the collision key. Wrapped with `PRAGMA foreign_keys = OFF/ON` (outside the transaction) to tolerate historical databases that arrived at v7 with stale FK clauses still attached; integrity is enforced by an explicit orphan check inside the migration.
- **v8→v9:** Eviction infrastructure — adds `tombstoned_at TEXT NOT NULL DEFAULT ''` on entities, observations, and relations; adds `last_accessed_at TEXT NOT NULL DEFAULT ''` on entities, backfilled from `updated_at`. Supports the four-tier degradation chain (§12).
- **v9→v10:** Source-instance provenance — adds `source_instance TEXT NOT NULL DEFAULT 'unknown'` on observations (which machine wrote it), backfilled to 'fedora'. Race-tolerant ALTER (concurrent server instances migrate in parallel — Issue #78 pattern).
- **v10→v11:** FTS5 full-text index — external-content `obs_fts` table over `observations.content` (`content_rowid='id'`, unicode61 + remove_diacritics 2) with three sync TRIGGERS (insert/delete/update-of-content; triggers rather than code-sync so evict.ts's raw-SQL writes stay covered). Index holds ALL observations — active-only filtering is the query-time `superseded_at=''` join. `'rebuild'` indexes the pre-v11 corpus; the migration transaction is IMMEDIATE with an in-transaction version re-check so racing instances (Issue #78 deployment) skip the corpus-sized rebuild instead of serially repeating it — IMMEDIATE is load-bearing: a DEFERRED re-check would read a pre-commit snapshot and die on SQLITE_BUSY_SNAPSHOT. NOTE: `bm25()` is an FTS5 auxiliary function usable only in a plain full-text query — aggregate contexts and flattened subqueries both throw; queries use a MATERIALIZED CTE (per-row scores inside, joins/aggregation outside).
- **v11→v12:** Retrieval strengthening — `access_count INTEGER NOT NULL DEFAULT 0` on entities. **PARITY RULE:** increments at exactly the sites that write `last_accessed_at` (touch helpers + createEntities'/migrateFromJsonl's INSERTs seeding 1 + the four inline `updated_at`+`last_accessed_at` UPDATEs) — one concept, two columns; a new `last_accessed_at` write site must increment `access_count` too. No backfill (DEFAULT 0 = never counted → `activationScore` −Infinity → excluded from the activation list). Race-tolerant ALTER (Issue #78 pattern), IMMEDIATE transaction.
- **v12→v13:** Relation-vocabulary repair — DATA migration (no schema change): rewrites the 9 audit-approved drifted relation-type spellings (`RELATION_VOCAB_FIXES` in relation-types.ts — an explicit reviewed map, never an algorithm) on ACTIVE rows only; superseded history keeps its original spelling; collision duplicates are soft-retired (retire-before-rewrite per entry, so a collision partner CREATED by an earlier entry's rewrite is handled). Live-graph effect: 32 drifted edges → 26 rewritten + 6 collision-retired; 128 → 119 distinct active spellings. MERGE-GATE convention: re-run the drifted-spellings audit scan against the live DB before deploying any future map extension (a variant written after the audit would leak past the exact-string map).
- **v13→v14:** VALID TIME (bi-temporal-lite) — `valid_from`/`valid_until TEXT NOT NULL DEFAULT ''` on observations AND relations. Transaction time (created_at/superseded_at = when the DB learned/retired a fact) and valid time (when it was true IN THE WORLD) are now separate. Caller-supplied ISO 8601 Z only (no LLM date extraction); '' sentinel = unspecified → field ABSENT in output. Write surface: `set_observation_metadata` (validFrom/validUntil, null clears — add_observations keeps its string-array shape) + `RelationInput` on create_relations (reversed windows rejected at the boundary; a relation differing ONLY in valid-time from an existing active one is dedup-skipped — recipe: invalidate then re-create). Read surface: all observation/relation hydrations + entity_timeline (both sides — an invalidated relation's valid window is only naturally visible there). Supersede deliberately does NOT carry valid-time forward (new content = new claim). NO query filtering yet (DEF-RR-01). Race-tolerant ALTERs, IMMEDIATE transaction.
- **v17→v18:** Prospective memory + provenance (v1.7.0). CREATE TABLE `prospective_triggers` (id/trigger_text/payload/project/created_at/fired_at) + `ALTER observations ADD source_ref TEXT NOT NULL DEFAULT ''`. House race discipline: IMMEDIATE transaction + in-transaction version re-check + duplicate-column-tolerant ALTER (Issue #78 pattern), mirroring v16. The `vec_triggers` vec0 table is DELIBERATELY created in the vector-setup block (like vec_observations), NOT here — a versioned migration must succeed on a build with no sqlite-vec extension. '' sentinel on source_ref = unset (nothing to backfill; DEFAULT '' covers pre-v18 rows).
- **v16→v17:** Zero-width Cf strip — DATA migration (no schema change): `normalizeEntityName` now strips the Unicode Format (Cf) category (U+200B ZWSP, U+200C/D, U+FEFF, U+00AD, U+2060, …), so this migration recomputes `normalized_name` for EVERY entities row (active + superseded) from its display name and rewrites `relations.from_entity`/`to_entity` (endpoints store keys, so the rewrite is a direct Cf strip on the stored key — same result as the entity recompute). Collision guard on ACTIVE rows aborts + rolls back if two rows collapse to one key after stripping (naming both display forms + the key), mirroring v7→v8. Wrapped in `withForeignKeysDisabled` for the same reason v7→v8 is: a stale inline `REFERENCES entities(name)` clause makes any relations write raise "foreign key mismatch" (entities.name is only partially unique). Live-deployment note: a 2026-07-04 probe of the origin corpus found ZERO Cf chars and ZERO would-be collisions → verified no-op there; exists for arbitrary data. IMMEDIATE transaction with in-transaction version re-check (Issue #78 racing-instance pattern). Fixes Issue #59 (invisible copy-paste duplicate entities).
- **v15→v16:** Observation summary — `summary TEXT DEFAULT NULL` on observations, the ONE deliberate nullable-sentinel column (NULL = no explicit summary → getContextLayers' first-100-chars auto-fallback when building L1-index hints; an '' sentinel would be indistinguishable from a deliberately-blank hint). ≤200 chars enforced by Zod at the boundary. Race-tolerant ALTER, IMMEDIATE transaction.
- **v14→v15:** Embedding-model identity — ordinary single-row `vec_config(id CHECK(id=1), model_name)` recording WHICH model wrote `vec_observations`. Seeded with the HISTORICAL default (MiniLM), never the configured model (pre-v15 vectors can only be MiniLM's; seeding the configured name would let a first-run-with-new-model keep stale vectors). Startup guard: configured `EMBED_MODEL` ≠ recorded → loud log, `DELETE FROM vec_observations`, record new model, background sweep re-embeds — a mixed-model index is impossible, and a model switch/rollback is one env flip + restart.
